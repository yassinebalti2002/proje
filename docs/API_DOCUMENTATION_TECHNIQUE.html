1. Vue d'ensemble

L'API Maintenance Prédictive expose 22 endpoints HTTP couvrant la détection d'anomalie sur roulements (ensemble de 6 modèles ML non supervisés), l'estimation de durée de vie résiduelle (RUL), l'analyse spectrale, le reporting et le pilotage du pipeline de ré-entraînement. Cette documentation couvre uniquement la surface HTTP de l'API — pour l'architecture globale du système (moteur temps réel, dashboards, entraînement), voir DOCUMENTATION_TECHNIQUE.pdf.

CaractéristiqueValeur
Base URL (local)http://localhost:8000
Documentation interactive/docs (Swagger UI) · /redoc (ReDoc)
Format des réponsesapplication/json; charset=utf-8 (forcé explicitement)
AuthentificationEn-tête X-API-Key, 2 rôles (admin / opérateur)
Méthodes autorisées (CORS)GET, POST
Nombre d'endpoints22 (5 Système, 8 IA/Prédiction, 1 Reporting, 2 Alertes, 2 Données, 4 Pipeline)
Convention de lecture : chaque endpoint de ce document indique sa méthode HTTP, son chemin, son niveau d'authentification (public / opérateur ou admin / admin uniquement), sa limite de débit (rate limit), un exemple de requête/réponse et les codes d'erreur possibles.

2. Authentification

Implémentée dans auth.py. Système de clé API à 2 rôles (RBAC minimal), avec comparaison en temps constant (hmac.compare_digest) pour résister aux attaques temporelles.

2.1 En-tête requis

X-API-Key: <votre_clé>

Le nom de l'en-tête est configurable via la variable d'environnement API_KEY_HEADER (défaut : X-API-Key).

2.2 Rôles

RôleVariable d'environnementDroits
adminAPI_KEYS=cle1,cle2Tous les endpoints protégés, y compris /v1/pipeline/upload
operatorAPI_KEYS_OPERATOR=cle3,cle4Tous les endpoints protégés sauf /v1/pipeline/upload

Génération d'une clé sûre :

python -c "import secrets; print(secrets.token_hex(32))"

SituationCodeMessage
En-tête absent401En-tête X-API-Key manquant.
Clé invalide401Clé API invalide.

Chaque tentative (succès/échec) est journalisée dans logs/audit.log (JSON Lines) avec horodatage, résultat (GRANTED/DENIED/FORBIDDEN), rôle, IP, méthode, chemin, et une empreinte SHA-256 tronquée de la clé — jamais la clé en clair.

GET /, GET /health, /docs, /redoc, GET /metrics, GET /v1/model-card, GET /sensors, GET /anomalies, GET /v1/health-score/{id}, GET /v1/history/{id}, GET /v1/alert-level/{id}, GET /v1/results, GET /v1/spectral/{id}, GET /pipeline, GET /v1/alerts, GET /v1/alerts/stats.

3. Rate limiting

Implémenté dans rate_limiter.py — fenêtre glissante en mémoire, thread-safe, sans dépendance externe (pas de Redis).

  • Clé de comptage : (IP source, chemin) — pour les requêtes POST, le sensor_id extrait du corps JSON est ajouté à la clé (ip:chemin:sensor_id), pour que chaque capteur ait son propre quota plutôt qu'un quota partagé par IP sur /v1/predict.
  • Limite dépassée → 429 avec en-tête Retry-After: <secondes>.
  • Purge automatique des entrées inactives depuis plus d'1h (toutes les 5 min).
  • La limite par minute varie selon l'endpoint (5 à 60 req/min) — voir le tableau récapitulatif.
HTTP/1.1 429 Too Many Requests Retry-After: 12 {"detail": "Trop de requetes. Limite : 60 appels/60s par IP. Reessayez dans 12s."}
Limite connue : basé sur request.client.host, qui reflète l'IP du reverse proxy si l'API est déployée derrière un proxy sans proxy_headers=True configuré côté Uvicorn — dans ce cas, tous les clients externes partageraient le même quota.

7. Endpoints — Système

GET/ — public

Identité de l'API et liste résumée des endpoints principaux. Pas de rate limit.

GET/health — public

Health check — état des modèles chargés. Pas de rate limit.

{ "status": "ok", "models_loaded": true, "models": ["if", "lof", "ocsvm", "ecod", "hbos", "copod"], "features_count": 31, "version": "3.1.0", "n_sensors_in_memory": 19, "timestamp": "2026-08-07T10:00:00" }
GET/metrics — public · 30/min

Métriques de performance du modèle (source : models/metrics_v3.csv) : f1_score, accuracy, precision, recall, auc_roc, n_anomalies, n_total, contamination, weights (poids appris du stacking par modèle), window_size, n_features.

GET/v1/model-card — public · 30/min

« Model card » — provenance des données d'entraînement, méthodologie, limites connues, pour chaque composant (détection d'anomalie et RUL). Permet d'auditer la fiabilité d'une prédiction avant utilisation pour une décision critique.

GET/v1/system-limits — opérateur/admin · 30/min

Liste structurée (L1 à L6) des limitations techniques connues : alertes non persistantes par défaut, features d'accélération toujours nulles, absence de capteur de courant, pas de déploiement edge, RUL heuristique non validé sur pannes réelles, etc.

8. Endpoints — IA / Prédiction

8.1 POST /v1/predict

POST/v1/predict — opérateur/admin · 60/min (par IP + sensor_id)

Détection d'anomalie en temps réel via un ensemble non supervisé IF + LOF + OCSVM + ECOD + HBOS + COPOD, fusionné par stacking LogisticRegression. Un filtre de persistance temporelle (k=3 fenêtres consécutives par défaut) confirme l'anomalie avant de la remonter, pour réduire les faux positifs isolés.

Requête (minimum 1 mesure dans history) :

{ "sensor_id": "8f7f2f7e", "motor_id": "Motor_1604", "history": [ { "temperature": 32.5, "vibration_x": 266.0, "vibration_y": 273.0, "vibration_z": 280.0, "current": 0 } ] }

Réponse (200) :

{ "sensor_id": "8f7f2f7e", "motor_id": "Motor_1604", "timestamp": "2026-08-07T10:00:00", "prediction": "NORMAL", "is_anomaly": false, "confidence": 0.12, "votes": 1, "risk_level": "FAIBLE", "anomaly_score": 0.12, "individual_models": {"IF":"NORMAL","LOF":"ANOMALY","OCSVM":"NORMAL", "ECOD":"NORMAL","HBOS":"NORMAL","COPOD":"NORMAL"}, "individual_scores": {"IF":0.08,"LOF":0.61,"OCSVM":0.15, "ECOD":0.10,"HBOS":0.09,"COPOD":0.11}, "features": { "temp_mean": 32.5, "vib_total": 391.2, "health_score": 94.3, "...": "..." } }
ChampDétail
risk_levelFAIBLE (score<0.25) · MODÉRÉ (<0.50) · ÉLEVÉ (<0.75) · CRITIQUE (≥0.75) — reforcé à FAIBLE si health_score≥85 sans anomalie confirmée
votesNombre de modèles (0–6) dont le score individuel dépasse 0.5

Effets de bord : met à jour l'historique glissant du capteur, alimente le buffer de vibration brute, déclenche une alerte externe si risk_level est CRITIQUE ou ÉLEVÉ.

Erreurs : 400 si history vide.

8.2 POST /v1/predict-rul

POST/v1/predict-rul — opérateur/admin · 60/min

Estime le temps restant avant défaillance (RUL), en combinant score de dégradation instantané, tendance temporelle, historique d'anomalies récentes, et un modèle ML (GradientBoostingRegressor) qui peut aggraver (jamais atténuer) le niveau d'alerte de l'heuristique. Minimum 3 mesures dans history.

Le RUL est une estimation empirique — aucun modèle supervisé sur pannes réelles confirmées n'est disponible à ce jour. Ne pas utiliser comme seule base d'une décision d'arrêt machine.

Réponse (200) :

{ "sensor_id": "8f7f2f7e", "motor_id": "Motor_1604", "timestamp": "2026-08-07T10:00:00", "rul_hours": 456.2, "rul_days": 19.01, "degradation_rate": 18.4, "health_score": 94.3, "confidence": "MOYENNE", "alert_level": "OK", "recommendation": "Fonctionnement normal. RUL > 14 jours...", "trend": { "temp_trend": 0.42, "vib_total_trend": 3.1, "deg_instant": 0.21, "deg_rate": 0.05, "rul_model": "heuristic_CDC + ML_gradient_boosting" } }
ChampDétail
alert_levelOK (>14j) · ATTENTION (7–14j) · URGENT (3–7j) · CRITIQUE (<3j)
confidenceHAUTE (≥10 mesures) · MOYENNE (≥5) · FAIBLE (<5)

Garde-fou capteur sain : health_score≥85 force alert_level=OK avec un RUL plancher de 336h (14 jours).

Erreurs : 400 si moins de 3 mesures.

8.3 POST /v1/iot-predict

POST/v1/iot-predict — opérateur/admin · 60/min

Endpoint pensé pour la production sans accès base de données. Le client envoie une mesure à la fois ; le serveur maintient une fenêtre glissante de 20 mesures par sensor_id et retourne prédiction d'anomalie + RUL en un seul appel (RUL à null tant que moins de 3 mesures accumulées).

{ "sensor_id": "8f7f2f7e", "temperature": 32.5, "vibration_x": 266.0, "vibration_y": 273.0, "vibration_z": 280.0 }

Champs requis : temperature, vibration_x, vibration_y, vibration_z. Réponse : union des champs de /v1/predict et /v1/predict-rul, plus window_size.

8.4 POST /v1/spectral-analysis

POST/v1/spectral-analysis — opérateur/admin · 20/min

Analyse spectrale complète du signal de vibration : FFT (spectre de puissance, fréquences dominantes), analyse d'enveloppe (démodulation Hilbert), fréquences caractéristiques de défauts roulements (BPFO, BPFI, BSF, FTF — roulement SKF 6205-2RS), décomposition en ondelettes (CWT Morlet).

Requête identique à /v1/predict, plus paramètres query rpm (1450.0), fs (100.0 Hz). Minimum 8 mesures vibration_z.

Erreurs : 400 si moins de 8 mesures ; 503 si signal_processing.py indisponible.

8.5 GET /v1/spectral/{sensor_id}

GET/v1/spectral/{sensor_id} — public · 30/min

Version publique et en lecture seule : utilise le buffer serveur des dernières valeurs vibration_z déjà reçues via /v1/predict (pas de recalcul côté client, pensé pour le dashboard). Paramètres query : rpm, fs.

8.6 GET /v1/health-score/{sensor_id}

GET/v1/health-score/{sensor_id} — public · 60/min

Score de santé (0–100) normalisé par baseline propre au capteur (calculée sur ses 20 premières mesures) — évite le biais d'une comparaison à un seuil global identique pour tous les moteurs.

{ "sensor_id": "8f7f2f7e", "health_score": 91.4, "health_raw": 88.0, "baseline": 0.12, "score_method": "relatif_baseline", "anomaly_rate": 0.1, "n_records": 42, "last_score": 0.09, "trend": "STABLE", "timestamp": "2026-08-07T10:00:00" }

Si le capteur n'a aucun historique : health_score: 100.0, n_records: 0 (pas de 404 sur cet endpoint).

8.7 GET /v1/history/{sensor_id}

GET/v1/history/{sensor_id} — public · 60/min

Historique glissant des prédictions d'un capteur (en mémoire — réinitialisé au redémarrage, sauf persistance disque anomaly_history_persist.json). Paramètre query limit (défaut 20). Maximum en mémoire : 50 entrées par capteur.

Erreurs : 404 si aucun historique pour ce capteur.

8.8 GET /v1/alert-level/{sensor_id}

GET/v1/alert-level/{sensor_id} — public · 60/min

Niveau d'alerte consolidé sur les 10 dernières prédictions, pensé pour un feu tricolore de dashboard : alert_level OK (vert) · ATTENTION (jaune) · URGENT (orange) · CRITIQUE (rouge) · INCONNU (gris, si aucune donnée).

8.9 GET /v1/results

GET/v1/results — public · 60/min

Dernières prédictions (anomalie + RUL fusionnées) de tous les capteurs actifs, ou d'un capteur précis via ?sensor_id=. Mis à jour à chaque appel /v1/predict ou /v1/predict-rul. Erreurs : 404 si sensor_id fourni mais introuvable.

8.10 GET /sensors et GET /anomalies

GET/sensors — public · 60/min

Liste des capteurs actifs (source : historique temps réel en mémoire, sinon CSV historique).

GET/anomalies — public · 60/min

Anomalies filtrées par score minimum. Paramètres query : min_score (0.5), limit (100).

10. Endpoints — Pipeline (ré-entraînement)

Workflow complet de ré-entraînement à partir d'un dump SQL MariaDB (ai_cp), exécuté en arrière-plan (thread) : parsing SQL → CSV, entraînement des 6 modèles, rechargement à chaud dans l'API (sans redémarrage).

10.1 GET /pipeline

GET/pipeline — public

Sert la page HTML d'upload (pipeline_upload.html). Exclue du schéma OpenAPI.

10.2 POST /v1/pipeline/upload

POST/v1/pipeline/upload — admin uniquement · 5/min

Reçoit un fichier .sql (flux par blocs de 4 Mo, pour éviter de charger un dump de plusieurs centaines de Mo entièrement en mémoire), puis démarre en tâche de fond : parsing SQL (generate_dataset_from_sql.py), entraînement (train_model_v3_unsupervised.py), rechargement des modèles.

Requête : multipart/form-data — file (.sql, requis), train_mode ("full" ou "fast", défaut "full").

curl -X POST http://localhost:8000/v1/pipeline/upload \ -H "X-API-Key: <clé_admin>" \ -F "file=@dump_ai_cp.sql" \ -F "train_mode=full"
{ "job_id": "a1b2c3d4e5f6", "status": "running", "filename": "dump_ai_cp.sql", "size_mb": 87.4, "poll_url": "/v1/pipeline/status/a1b2c3d4e5f6" }

Erreurs : 400 si l'extension n'est pas .sql ; 401/403 selon le rôle de la clé — une clé opérateur valide reçoit 403, pas 401.

10.3 GET /v1/pipeline/status/{job_id}

GET/v1/pipeline/status/{job_id} — opérateur/admin · 60/min

Statut d'un job en cours — à interroger toutes les 2-3 secondes. Paramètre query since (défaut 0) : ne retourne que les logs postérieurs à cet index.

{ "job_id": "a1b2c3d4e5f6", "status": "running", "step": 4, "step_name": "Entraînement des modèles ML...", "progress": 58, "elapsed": "1m 12s", "new_logs": [{"text": "✅ LOF entraîné", "type": "s"}], "total_logs": 34, "results": null }

status : running · done · error. results (non nul une fois terminé) inclut auc, f1, n_measures, n_anomalies, top_anomalies.

Erreurs : 404 si job_id inconnu.

10.4 GET /v1/pipeline/jobs

GET/v1/pipeline/jobs — opérateur/admin · 30/min

Liste des 10 derniers jobs de pipeline (résumé : job_id, status, filename, progress, elapsed, created_at).
